# Аудиосвязь в LAN / Wi-Fi: требования

Всё ниже, кроме отмеченного «проверено», **не проверено на двух реальных компьютерах**. Проверки T05 шли в одном
Linux-контейнере (два браузерных контекста, loopback и второй адрес того же хоста). Это не доказывает работу по LAN/Wi-Fi.

## Безопасный контекст (микрофон)

| Где открыта страница | `getUserMedia` |
|---|---|
| Пульт на ПК преподавателя `http://127.0.0.1:8765` | есть (localhost — secure context) — **проверено** |
| Любая страница с другого ПК по `http://192.168.x.x` | **нет** (не secure context) — **проверено** на втором адресе того же хоста: студент получает `insecure_context` |
| Страница по `https://` с доверенным сертификатом | есть — **проверено** на втором адресе того же хоста с тестовым CA |
| Приложение студента Electron (`qorgau://app`, зарегистрирован как secure) | есть, если оболочка разрешит аудио (см. STUDENT_INTEGRATION.md) — **не проверено** |

Пульт преподавателя по протоколу v1 доступен **только с loopback** — открывать его с другого компьютера не нужно и
нельзя (сервер отвечает 403, **проверено**). Флаги вроде `--unsafely-treat-insecure-origin-as-secure` или
отключение проверок сертификатов — не решение.

## Сигнализация: нужен WSS на LAN

`qorgau.class.v1` описывает `ws://` для студентов. Звук шифруется DTLS-SRTP, но отпечатки DTLS приходят в SDP по
сигнализации: злоумышленник в той же сети, перехватив `ws://`, может подменить отпечатки и встать посередине.
Для реального класса: `wss://` + в приложении студента закрепить сертификат сервера (pinning по SHA-256, отпечаток
показать в пульте) или выпустить сертификат от локального CA, которому доверяют ПК класса.
DEV-сервер поддерживает `--tls-cert/--tls-key`; путь HTTPS/WSS **проверен** только на одном хосте (тестовый CA в
отдельной NSS-базе браузера). Изменение `ws://` → `wss://` в v1 — решение T01/A01.

## Сеть

* Оба ПК в **одной подсети**, без изоляции клиентов на точке доступа (в школьном/гостевом Wi-Fi её часто включают —
  тогда не будет ни WebSocket, ни звука). STUN/TURN нет (интернет не используется) — через NAT/VLAN звук не пройдёт.
* WebRTC использует **UDP** на случайных портах обоих ПК; брандмауэр Windows должен разрешать входящий UDP для
  браузера преподавателя и для приложения студента (Windows спросит при первом запуске — разрешает человек).
* TCP 8765 на ПК преподавателя — для `/ws/student` (Windows спросит для Python при первом запуске сервера).
* **mDNS.** Chromium скрывает локальные IP за именами `*.local`, если странице не дано разрешение микрофона.
  В режиме «только слушать» браузер преподавателя микрофон не запрашивает → его кандидаты — `.local`. Соединение
  обычно всё равно устанавливается (студент с разрешённым микрофоном отдаёт настоящий IP, преподаватель узнаётся как
  peer-reflexive), но если multicast (UDP 5353) в сети заблокирован и микрофона нет ни у одной стороны (студент только
  слушает преподавателя), соединение может не установиться. Варианты: разрешить микрофон пульту заранее; политика
  Chrome `WebRtcLocalIpsAllowedUrls` для `http://127.0.0.1:8765` на ПК преподавателя. **Не проверено.**
* Полоса: Opus ~30–50 кбит/с в каждую сторону; для одного разговора несущественно.

## Минимальная проверка на месте (2 ПК, до демо)

1. ПК преподавателя: `python -m qorgau_class_audio.devserver --host 0.0.0.0 --port 8765` (+ `--tls-cert/--tls-key`).
2. ПК студента: открыть `https://<ip-преподавателя>:8765/test-peer/` (с доверенным сертификатом) или приложение студента.
3. Слушать / говорить / завершить; выключить Wi-Fi у студента на 5 с; включить; «Подключиться снова».
4. Записать: версии ОС и браузера, тип сети (кабель/Wi-Fi), сработало ли без правок брандмауэра.

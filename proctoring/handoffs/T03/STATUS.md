## Что работает
**Сервер** — FastAPI-роутер + `ReviewStore` для монтирования в сервер класса C1:
* **Приём эпизодов** из `/ws/student` (`ingest_incident`):
  * поля проверяются;
  * дедупликация по `(student_id, seq)`;
  * одна запись на `(student_id, incident_id)`: кадры и обновления не создают новых эпизодов;
  * старый `seq` не перезаписывает новый, закрытый эпизод не открывается заново;
  * снимок ≤ 40 КБ (если есть) сохраняется.
* **`POST /api/student/clips/{incident_id}`** — приём клипа:
  * доступ по `Bearer <resume_token>`, через инжектируемый resolver C1;
  * только для своего эпизода и только после запроса преподавателя;
  * только `video/mp4` или `video/x-msvideo`, ≤ 8 МБ, лимит соблюдается и при chunked-загрузке;
  * формат проверяется по байтам: обход блоков MP4 (`ftyp`, `moov`, обрезанные файлы) и RIFF/AVI;
  * определяются кодек, длительность и faststart;
  * имена файлов случайные, запись атомарная, хранилище вне исходников;
  * повтор тех же байтов → 200 `duplicate`; другие байты → 409, доказательство не заменяется;
  * гонка параллельных загрузок обработана (150 стресс-прогонов, 0 ошибок);
  * отклонённый файл переводит клип в «недоступен» с причиной.
* **`GET|HEAD /api/teacher/clips/{incident_id}`** — выдача клипа:
  * `Range` / 206 / 416 / `If-Range` / `ETag` — перемотка в `<video>`;
  * перед первой выдачей сверяется SHA-256: подменённый файл → 500 `clip_integrity`, пропавший → 404;
  * `?student_id=` снимает неоднозначность.
* **Состояния клипа:** `not_requested` → `loading` («клип загружается») → `available` («доступен»), либо
  `unavailable` («недоступен») с причиной: `not_recorded`, отказ студента (`ack ok=false`), таймаут 120 с,
  отклонённый файл. Повторный запрос возможен.
* **`GET /api/teacher/students/{id}/incidents`** — эпизоды в полях протокола, которые читает T02, плюс:
  * `decision_note_ru`, `decision_history[]`, `clip{state,…}`, `snapshot_available`;
  * объект `review`: зона по сигналам студента и зона с учётом решений.
* **`POST /api/teacher/students/{id}/decision`** — решения:
  * значения `confirmed`, `dismissed`, `needs_followup` («Недостаточно данных»), комментарий ≤ 1000;
  * журнал только на добавление (UPDATE/DELETE запрещены триггерами), `supersedes` указывает на прошлое решение;
  * двойной клик в пределах 5 с не создаёт дубля.
* **Оценка риска:** отклонённые эпизоды исключаются из входа ОБЩЕГО правила A05
  `proctor.fusion.zones.assess_session_zone` — правило не копируется. Подтверждённые, «недостаточно данных» и
  непроверенные эпизоды учитываются. Неизвестное покрытие → серый, никогда не зелёный. Зона студента
  показывается рядом без изменений. Семантика вынесена на подтверждение (DEPENDENCIES №5).
* **Перезапуск:** SQLite (WAL, `synchronous=FULL`, миграции по `user_version`) + файлы. После перезапуска
  сохраняются эпизоды, клипы, запросы, решения и память дедупликации.

**Панель преподавателя** (`classreview/ui/`) — модуль слота `history` в реестре T02:
* шкала времени и список эпизодов: время, правило, приоритет проверки (иконка + текст), длительность,
  решение, состояние клипа;
* карточка эпизода: описание, начало, длительность, приоритет, категория;
* блок клипа со всеми состояниями и кнопкой «Запросить клип / Запросить снова»;
* плеер с перемоткой; метка «ТЕСТОВЫЙ КЛИП: не запись реального студента»;
* «Скачать клип» для форматов, которые браузер не воспроизводит;
* три решения с комментарием и журнал изменений;
* весь текст выводится через `textContent`; опрос сервера не пересоздаёт играющее видео.
Есть DEV-страница и `register.js` для панели T02.

**Клиент студента:** `CLIENT_CLIP_UPLOAD.md` (точные требования и метаданные), `examples/upload_clip.py`
(stdlib, идемпотентные повторы) и `examples/fake_student.py` (СИНТЕТИЧЕСКИЙ студент, протокол целиком).
**DEV-стенд:** `devserver.py` — явно помеченная замена нужных частей C1, это НЕ сервер класса.

## Не проверено / ограничения
* Нет сервера C1 и uplink C2: проверено на DEV-стенде и в изолированной панели T02. Нужна интеграция по
  DEPENDENCIES №8.
* Windows: SQLite/файлы, браузер Edge, H.264 не запускались. Chromium из Playwright не декодирует H.264, поэтому
  тестовые клипы — VP9 в MP4. Совет клиенту «H.264» основан на поддержке кодека в Edge/Chrome, у нас не измерен.
* Реальные клипы с камеры студента не создавались: это задача другого разработчика. Есть только синтетические
  клипы с надписью «TEST CLIP».
* Блокировка перебора PIN в DEV-стенде не реализована (только loopback); вход в реальной системе — у C1.
* Удаление и срок хранения клипов не реализованы: протокол v1 этого не задаёт; лучше через T01.
* Клиент на TS (панель) тестировался через Chromium e2e, отдельных unit-тестов JS нет.

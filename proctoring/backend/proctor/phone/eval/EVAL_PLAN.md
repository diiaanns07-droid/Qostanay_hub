# A03 — план проверки качества обнаружения телефона

Статус на 2026-10-08: **клипов экзаменационного ракурса нет → точность событий (phone_visible / phone_raised /
possible_screen_capture) NOT EVALUATED.** Есть только детекторная проверка на общих фотографиях COCO val2017
(см. `handoffs/A03/STATUS.md`), она не описывает веб-камеру ноутбука и не оценивает временные сигналы.

## Что разделяем

| Проверка | Инструмент | Что доказывает | Чего НЕ доказывает |
|---|---|---|---|
| Unit-тесты с fake boxes | `pytest backend/proctor/phone/tests` | логика трекинга/сигналов/контракта, обработка ошибок | ничего о CV-точности |
| Реальный inference | `tests/test_real_model.py`, `python -m proctor.phone.prepare --check` | модель грузится локально, sha256, CPU-latency | точность |
| Детектор на фото | `python -m proctor.phone.eval.images` | P/R бокса «cell phone» на общих фото с знаменателями | экзаменационный ракурс, подъём, съёмку |
| События на клипах | `python -m proctor.phone.eval.clips` | event/clip-level P/R на записанных клипах | production-точность (выборка мала) |

## Датасет (dataset_manifest.json)

Позитивы: телефон в руке (грудь), подъём с колен/стола, тыльная сторона к экрану, экран к веб-камере, край кадра,
маленький объект, блики/отражения, слабый свет. Hard negatives: калькулятор, кошелёк, очки/футляр, блокнот,
обычная работа без предметов (для ложных тревог в час). Только добровольные записи с согласием или
лицензированные материалы; медиа вне Git; ссылки по пути + sha256.

## Протокол записи (на демо-ноутбуке, камера только через A02)

1. Запись через A02 (live → replay), 640×480, 8–15 fps, разные люди/освещение/фон. Без посторонних лиц.
2. Извлечь кадры в каталог (`frames/<clip_id>/000001.jpg …`) средствами A02/ffmpeg; этот модуль видео не открывает.
3. Разметка интервалов в мс от начала клипа: `phone_visible` — телефон хотя бы частично виден;
   `phone_raised` — телефон поднят выше линии груди (зона: центр бокса выше `raise_zone_y_max=0.60` кадра) или
   поднимается туда; `possible_screen_capture` — телефон удерживается неподвижно тыльной стороной к монитору
   (размечается по сценарию записи, т.к. по веб-камере направление камеры телефона не определяется).
4. Разбиение по `subject_group` (человек + сессия): `tune` (подбор порогов) и `test` (итог). Кадры одного клипа
   никогда не попадают в обе части; инструмент падает при утечке группы.

## Метрики и отчёт

* Событие: совпадение при перекрытии ≥ 200 мс после расширения размеченного интервала на ±500 мс; предсказанные
  отрезки с разрывами ≤ 500 мс сливаются, короче 250 мс отбрасываются (параметры в манифесте клипов).
* Отчёт: event precision/recall в виде `k/n`, доля позитивных клипов с попаданием, доля негативных клипов с ложной
  тревогой, список пропусков и ложных тревог, диапазон условий, `config_version` и sha256 модели.
* Для выборки в десятки клипов формулировка только вида «сработало в k из n записанных клипов при условиях …».

## Ограничения, которые нужно показывать честно

* Детектор «cell phone» (COCO) не различает экран и тыльную сторону; направление камеры телефона не наблюдаемо.
  `possible_screen_capture` — только шаблон «телефон неподвижно, крупно, в центре верхней зоны», иначе
  `insufficient_evidence`. Телефон вне поля зрения веб-камеры не виден вообще.
* Калькулятор отсутствует среди классов COCO — ложные срабатывания на нём надо измерять на клипах.
* Ни один сигнал не является доказательством фотографирования или списывания; решение — за преподавателем.
